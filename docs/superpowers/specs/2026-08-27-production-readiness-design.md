# Hungry Spot Production Readiness Design

## Goal

Make the existing Android customer application safe to submit to Google Play
and credible as a public LinkedIn/GitHub portfolio project without changing the
working cart, checkout, navigation, or Stripe payment behavior.

## Decisions

- Use `com.malikhassanjavaid.hungryspot` as the permanent Android namespace
  and application ID.
- Keep `flutter_stripe` 12.1.1 and its matching platform packages until the
  upstream Android CardField focus regression is closed. Fix the current R8
  release failure with explicit generated warning rules instead of upgrading.
- Target API 36 and minimum API 24.
- Require a local ignored upload keystore for production signing. Never commit
  keystore passwords or private keys.
- Use the Hungry Spot burger/fries mark for adaptive Android and iOS icons.
- Convert large menu photography to WebP, retain visual transparency, cap the
  longest dimension at 1440px, and update every asset reference atomically.
- Put privacy and account management behind shared configuration and a
  dedicated service. The app must provide an in-app account deletion request;
  Firebase Functions performs authenticated server-side data deletion.
- Publish static privacy and external account-deletion pages from `docs/`.
  Public contact email remains build/config driven until the owner confirms it.

## Release architecture

Android Gradle reads an ignored `android/key.properties` and refuses to sign a
production release with debug credentials. `proguard-rules.pro` contains only
the Stripe push-provisioning warnings generated by R8. Firebase must contain an
Android app registered for the permanent package before the old
`google-services.json` is replaced.

## Account deletion architecture

`AccountService` invokes a callable `deleteAccount` function. The function
requires Firebase Authentication, deletes owned cart/profile data, orders, and
server-only Stripe verification documents in bounded batches, then deletes the
Firebase Auth user. The UI requires a destructive confirmation and re-login
guidance when Firebase requires recent authentication. Firestore continues to
deny client-side deletes.

The external deletion page explains what is deleted, what payment/order data
may be retained for legal or fraud-prevention obligations, and provides the
confirmed public support contact.

## UX and accessibility

- Expose Privacy & Account from Profile and Privacy Policy from Login.
- Keep all destructive actions visually distinct and confirmation-gated.
- Ensure onboarding Skip has a 48dp minimum target and progress semantics.
- Preserve inline authentication validation and existing semantic labels.
- Retest text scaling, TalkBack order, and physical-device startup after asset
  optimization.

## Verification

- Widget/unit tests for configuration, legal entry points, account deletion
  states, and profile navigation.
- Node tests for the deletion function's ownership and batch behavior where
  feasible; lint the Functions source.
- `flutter analyze --no-pub` and the complete `flutter test` suite.
- Successful signed `flutter build appbundle --release` using ignored local
  production configuration.
- Install/run a release APK on an API 36 emulator and capture stable entry
  screens.

## Non-goals

- No payment-flow redesign or Stripe major upgrade.
- No staff, rider, analytics, subscriptions, or order-tracking expansion.
- No production deployment to Firebase or Google Play without the owner's
  final cloud-console credentials and legal contact confirmation.
